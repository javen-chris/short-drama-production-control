# 前台运行审查工具 · 操作手册

> 适用范围：`<项目>/workflow/` 下有运行轨迹的所有短剧项目
> 对应代码：短剧生产线控制台 `tools/render_run_report.py` + `src/production_control/run_report.py` + `run_server.py`
> 最后核对：2026-09-21（控制台 main @ `1836894`，PR #1–#25 已合并，pytest 123 通过）

---

## 一、这个工具是干什么的

它是一个**纯本地的进度看板**，用来回答三个问题：

1. **现在跑到哪一步了**（当前段、当前步、已完成几步）
2. **每一步有没有留下证据**（每步引用的协议与产物文件路径）
3. **有没有卡住等我做决定**（等待批准 / 阻断 / 挂起）

它不是"下一个浏览器 + 静态 HTML 文件"，而是**一个临时起在本机的小服务**。这一点很关键：
浏览器打开本地 HTML 文件时读不到同目录的 JSON（浏览器安全限制），而起了服务之后，
**每次刷新都会重新读取磁盘上的轨迹文件**，所以永远是最新状态——哪怕 Agent 正在跑。

**它只读、不动生产流程**：关掉黑窗口服务就停了，Agent 的记录行为完全不受影响；
重开会重新读取最新文件。唯一的写入例外是页面上的"段清单"编辑（见第六节）。

服务只绑定 `127.0.0.1`，**只有你自己这台机器能访问**，不会暴露到局域网。

**随仓库发布的通用启动器**（推荐，路径是相对的，仓库挪到哪都能用）：


## 三、命令行参数完整清单

```
python tools/render_run_report.py <target> [选项]
```

**`<target>`** 可以是三种东西，工具会自动识别：

| 传什么 | 看到什么 |
|---|---|
| 项目目录 | 整局总表（所有段） |
| `<项目>/workflow/run_index.json` | 同上 |
| `<项目>/workflow/runs/<某个>.json` | 单独那一段的逐步明细 |

**选项：**

| 参数 | 作用 |
|---|---|
| `--serve` | 起本地实时服务（默认自动打开浏览器） |
| `--port <数字>` | 配合 `--serve`，默认 **8765** |
| `--no-open` | 配合 `--serve`，不自动开浏览器（自己粘网址） |
| `--html <路径>` | **导出一份独立的静态 HTML 报告**（归档/发给别人用） |
| `--json` | 输出 JSON 格式的摘要，而不是给人读的文本 |
| `--no-details` | 跳过每段"逐步细节"，总表更短（段多时很省眼） |

**典型组合：**

```bat
:: 实时看，指定端口
render_run_report.py "<项目>" --serve --port 8800

:: 导出静态快照归档（不启服务）
render_run_report.py "<项目>" --html "D:\...\EP02_本轮快照.html"

:: 给脚本/别的工具消费
render_run_report.py "<项目>" --json > 摘要.json

:: 段很多时只看进度概况
render_run_report.py "<项目>" --no-details
```

## 四、页面怎么读

### 主视图 `/`
默认显示**正在进行中的那一段**（不是 20 段的大表格）。要点：

- **当前步**——一眼看到跑到哪
- **进度 x/y**——已完成步数 / 流水线总步数
- **步骤明细**——每步列出：引用的协议文件、落盘证据路径、校验器、时间
- **等待你决定 / 阻断 / 挂起**——有这类状态会显式标出来，这才是你该介入的信号

想看别的段，网址后面加 `?run=<run_id>`，比如 `http://127.0.0.1:8765/?run=RUN-EP02-N3-A2`；
页面上也可以直接点旁边的段列表切换。

### 全剧总览 `/overview`
一集有很多段时用这个，看整体推进到了哪。

### 关于"状态标签"的一个已知变化
早期版本会把不认识的状态值（`SUBMITTED_IN_PROGRESS` 这类中间态）误标成"未开始/已完成"。
**PR #22 起改为显示原始值**，所以看到 `SUBMITTED_IN_PROGRESS` 这种原文是正常的——
它代表"已提交、尚未回执"，别误读成已完成。

## 五、网址路由速查

服务起来后，`http://127.0.0.1:<端口>/` 的各个地址：

| 路径 | 返回 |
|---|---|
| `/` 或 `/index.html` | 主视图（当前段；`?run=<id>` 可切段） |
| `/overview` 或 `/all` | 全剧总览（所有段一屏） |
| `/run/<run_id>` | 单独某一段的页面 |
| `/data` | 总表 JSON（给脚本用） |
| `/run/<run_id>/data` | 单段 JSON |
| `/api/segments` | GET 取段清单；**POST 写回段清单**（唯一写入通道） |
| `/text` | 纯文本版总表 |
| `/health` | `{"status":"ok"}`，用来确认服务还活着 |

排查时先敲 `/health`：通就是服务活着、问题在渲染／数据；不通就是服务没起来。

## 六、页面上能改的东西（唯一写路径）

页面可以**补段名 / 备注**，保存后会写入 `<项目>/workflow/segments.json`——
和 Agent 读的是**同一个文件**。所以你在页面上补的段名，Agent 下一步就能看到。

这是整个服务唯一的写入动作，其余全是读。写入是增补/修正段清单，不会删你的轨迹。

## 七、配套：Agent 侧怎么"记一步"

看板的数据来自 Agent 每步的落盘。工具同样是一条命令（`tools/append_event.py`，协议 18 号）：

```bat
python tools\append_event.py "<项目目录>" ^
  --run RUN-EP02-N3-A2 ^
  --step short-drama-production-router ^
  --protocol 00_自动化生产唯一入口_v3.0.md ^
  --protocol 核心自动化生产包/02_任务路由与Gate_v3.0.md ^
  --evidence workflow/G0_上下文锁定_N3-A2.md
```

遇到需要你拍板的：

```bat
python tools\append_event.py "<项目>" --run RUN-EP02-N3-A2 ^
  --step short-drama-production-qa --outcome WAITING_APPROVAL ^
  --reason "G5 Prompt QA 完成，等你审阅后决定是否提交"
```

**两条硬约束（PR #21 起生效，重要）：**

1. `--evidence` 指向的文件**必须真实存在**，否则直接拒绝。
   理由很直接：指向一个不存在的文件，等于轨迹开始宣称自己拿不出的东西。
   正确顺序是**先写证据文件，再记这一步**。
2. 这一步确实没有自己的产物时，才显式加 `--allow-missing-evidence`；
   完全不传 `--evidence` 会给一条警告。别把它当默认用法。

记完不用重启任何东西，**回页面刷新一下**就能看到。

### outcome 合法值（PR #23 起已统一）
早期版本这里三方不一致：CLI 只收 4 个值、报表只认 5 个、Python API 对其余值**静默不改段状态**——
导致"事件记进去了、段状态却没动"，而 `SUBMITTED_IN_PROGRESS` 这类真实状态根本没法用这条命令记录。

现在统一由 `production_control/outcomes.py` 定义，**8 个合法值**：

| outcome | 含义 | 是否推进完成 |
|---|---|---|
| `COMPLETED` | 已完成 | 是 |
| `COMPLETED_WITH_CONTINUITY_CAVEAT` | 已完成（连续性存疑） | 是 |
| `USABLE_WITH_SCENE_CONTINUITY_FAIL` | 可用（场景连续性未过） | 是 |
| `SUBMITTED_IN_PROGRESS` | 已提交，等待回执 | 否（段状态改为该值） |
| `WAITING_APPROVAL` | 等待你批准 | 否 |
| `PAUSED_EXCEPTION` | 已挂起（异常） | 否 |
| `BLOCKED` | 已阻断 | 否 |
| `FAILED` | 失败 | 否 |

两个要点：

1. **未知值会被直接拒绝**（抛错并列出全部合法值），不再静默吞掉。
2. **带保留意见的完成不会被压平**——`COMPLETED_WITH_CONTINUITY_CAVEAT` 跑完仍显示该状态，
   不会被记成干净的"已完成"。这关系到能不能如实反映失败教训，别手工改成 `COMPLETED`。

## 八、排错速查

| 现象 | 原因与处理 |
|---|---|
| 提示"没有找到 …run_index.json，该项目还没有运行轨迹" | 这个目录还没跑过。先用编排器跑一段再来查看 |
| 端口被占用 | 工具会自动从 8765 一路试到 **8775**。以黑窗口里实际打印的那个网址为准，不用手动改 |
| 双击 cmd 后一闪而过 | 看 php/python 路径。脚本会先试 `python`，找不到才回退 hermes venv；两者都缺时请先装好 Python 或改 cmd 里的 `PY=` |
| 页面数据不更新 | 每次请求都重读磁盘（`Cache-Control: no-store`）。真不更新就确认 Agent 是不是把轨迹写到了**另一个**项目目录 |
| 关了黑窗口，页面打不开 | 正常。黑窗口就是服务本体。重新双击 cmd 即可 |
| 想确认服务活着 | 访问 `/health`，返回 `{"status":"ok"}` 即正常 |
| 报错"argument --outcome: invalid choice" | 状态值拼错或不在 8 个合法值内。见第七节的合法值表（PR #23 起未知值一律拒绝，不再静默吞掉） |
| 本地跑 `pytest` 全套卡住不退出 | 环境里设了 `HTTP_PROXY`（常见于各类 agent/沙箱终端），测试访问 `127.0.0.1` 会被发给代理而假死。跑测试前先 `env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy no_proxy=127.0.0.1,localhost` |

## 九、使用建议（按重要程度）

1. **把黑窗口开着，别用完就关。** 它不是一次性工具，服务活着＝随时能刷最新进度。
   建议看板常驻，比反复问 Agent"跑到哪了"高效得多。

2. **看到"等待批准/阻断"再去介入。** 这三类状态是工具专门为你留的介入信号；
   其余时候让它跑，别每步都问——这也是 18 号协议想要的效果。

3. **用 `--html` 做里程碑归档。** 每集收工、或每段到某个里程碑时导出一份静态快照。
   注意：静态导出**不含任何交互控件**（这是刻意设计，PR #19），所以它只是"照片"，
   要能刷新的东西还是得靠服务。

4. **导出前让 Agent 先补完该落的证据。** 导出的快照会带上当时每一步的证据路径；
   证据没落就导出，等于把空洞也归档了。

5. **多段项目善用 `--no-details`。** 20 段的详细总表没人看得下去，先看概况、
   再对某一段用 `?run=<id>` 下钻，眼睛负担小很多。

6. **轨迹文件和项目一起备份。** 页面本身是无状态的——所有真相都在
   `<项目>/workflow/run_index.json` 和 `runs/*.json` 里。备份这些就等于备份了整局的所有痕迹。

7. **一个项目别同时开两个服务。** 工具会自动换端口不报错，但你容易搞混哪个窗口对应哪个项目。
   要并行开就显式指定不同 `--port`。
