# 短剧生产看板任务知识库｜实施策略

## 一、目标与边界

知识库帮助 Agent 解释自然语言任务、找到协议依据、提出所属 Gate 和检查项；看板只用确定的 ID、可核验的证据和独立 QA 结论改变流程状态。知识库不能自行签发 PASS，也不能替代付费授权。

正式步骤的唯一注册处仍是 `skills/skill-chain.json` 的 `steps`。同文件的 `gate_checks` 定义 Gate 内检查项与历史活动别名；它们不会增加正式步骤进度。协议原文仍在仓库外的 `短剧制作核心协议`。历史轨迹保持原样。

## 二、当前已落地的最小知识层

`gate_checks` 每项有稳定 `id`、`gate`、`name_zh`、`purpose_zh`、`decision_zh`、`kind`、`activity_names`、`counts_as_step_progress` 和 `protocol_refs`。其中 `purpose_zh` 说明辅助活动实际检查什么，`decision_zh` 说明它如何影响 Gate；`counts_as_step_progress` 必须为 `false`，防止辅助活动冒充正式步骤。`kind=required` 是放行前必须核验的门禁；`rework`、`exception`、`change` 分别是返工、异常与范围变更。`superseded_by` 只表示旧证据对应的范围已改变，显示“需复核”，绝不自动变成 PASS。

18 个历史名称中，17 个映射到检查项；`protocol-attestation` 是已有的 M02 标记。新增的未知活动继续原样显示，并进入待归类计数。三次 GLM HTTP 400 调度失败归在同一个 QA 异常检查项里；调用次数与有效 QA 结论必须分开。

## 三、后续数据契约

新事件建议保留原始动作文字，并增加以下机器字段；既有 `step`、`outcome`、`evidence` 不删除：

```json
{
  "step_id": "S12",
  "check_id": "C66",
  "activity": "platform-compliance-readback",
  "gate": "G6",
  "kind": "required",
  "provider": "libtv",
  "unit_id": "EP03_A1_MAIN_13S",
  "prompt_version": "v2",
  "contract_sha256": "<hash>",
  "evidence": "workflow/QA/<report>.md",
  "outcome": "BLOCKED"
}
```

字段规则：`step_id` 只接受步骤注册表中的 ID，且子任务允许为空；`check_id` 只接受检查项 ID；`unit_id` 用来隔离主片与补充片；`provider` 使同类任务能区分 RunningHub、小云雀和 LibTV；`prompt_version` 与 `contract_sha256` 用来发现旧证据。一个辅助动作不能通过填写 `step_id` 冒充该正式步骤已完成。

## 四、检索与判定顺序

1. 按稳定 ID 精确匹配正式步骤、检查项和标记。
2. 按注册表别名与规范化名称匹配，必须保留原始输入。
3. 按协议文件名、Gate、平台、生产单元和错误码做本地全文检索。
4. 仅在前三级无唯一结果时，让模型提出候选：候选 ID、依据段落、置信度、缺失证据及反例。模型不能直接写最终归类或 PASS。
5. 由确定性校验器核对来源版本、证据路径、资产哈希、平台回读、QA 模型独立性与授权范围；不满足时维持待核验或阻断。
6. GLM 独立 QA 给出结论后才可写入有权限的 QA 事件；生产模型只提交证据。模型名称字段本身不能充当身份认证，未来若跨进程写入，需由调用方凭据/签名证明写入者。

## 五、资料优先级与更新机制

优先级：用户当前裁定 → 核心协议入口和适用 Gate 原文 → 项目当前合同/已确认资产 → 步骤注册表/检查项 → 当次平台回读与独立 QA → 历史案例。历史案例只能提供线索，不能覆盖当前合同。检索结果要带文件路径、协议版本、哈希、适用 Gate/平台、读取时间。

协议升级时先核对核心协议文件名与内容，再同步 `skill-chain.json` 的 `protocol_refs`、协议指纹清单及相关校验要求；新增检查项只改注册表的 `gate_checks`。每条历史别名只能属于一个检查项，CI 对重复别名报错。

## 六、看板呈现

主视图仍是 G1–G6 六张卡。G5 展示 G5.1 审计、Prompt 返工及独立 QA 调度；G6 展示本地资产、目标项目、旧节点、模型预检、平台绑定、合规回写、节点回读和范围变更。卡片只显示状态与最重要阻断；展开后查看全部检查项与原始证据。未知活动留在“待归类”，绝不静默隐藏。

状态至少区分：未见记录、已提交待核验、阻断、范围已变需复核、独立 QA 通过。平台返回 `valid=true`、节点创建成功或文件上传成功，都不能自动提升为独立 QA 通过。新生产单元必须重新计算状态，不能继承旧单元的 PASS。

## 七、实施顺序与验收

**第一轮（本次）**：登记 18 个历史名称的语义归属，渲染 Gate 内检查项，保留原始轨迹和正式进度不变。以 EP03/A1 核对 17 个辅助名称加 1 个标记全部有去处，`resourceIds=[]` 仍显示阻断，旧节点在主片范围变更后显示需复核。

**第二轮**：扩展事件 schema 和写入工具，加入 `check_id`、`unit_id`、`provider`、证据版本；GLM 写入独立 QA 结论时校验真实身份与审计角色；建立从新事件到检查项的确定性映射。迁移历史时只生成派生索引，不重写原轨迹。

**第三轮**：为核心协议与项目当前文件建立本地全文索引，再加模型候选归类。保留检索引用与人工复核入口。记录误归类率、未知活动数、重复别名数、门禁误放行数；目标是门禁误放行始终为零。

验收用例：同义动作跨模型写法应归到同一检查项；RunningHub/小云雀/LibTV 的任务不能串平台；QA HTTP 400 不能变 PASS；新 Prompt 版本使旧 Skill 审计失效；上传成功但 `resourceId` 缺失仍阻断；历史 18 条全部可回看且不增加正式步骤完成数。
