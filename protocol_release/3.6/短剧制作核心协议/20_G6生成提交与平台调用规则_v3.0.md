## 二、两种提交模式（必须显式二选一）

提交报告里必须写 `submission_mode`，**不允许留空、不允许两种都写**。

| 模式 | 含义 | 允许条件 |
|---|---|---|
| `AUTONOMOUS_SUBMIT` | **Agent 代提交**：由 Agent 调用平台接口/CLI 完成真实提交 | `authorization.scope` ∈ {`test_submission`, `full_segment`, `within_budget`}，且 `submission_index <= max_submissions` |
| `HUMAN_FINAL_CLICK` | **人工最终点击**：Agent 只准备到"待提交包"，**提交动作由用户完成** | `authorization.scope == qa_only`，或用户明确要求自己点 |

**判定规则（按优先级）**：

1. 指令只授权到 QA（"QA 通过再说""先别提交"等）→ **强制 `HUMAN_FINAL_CLICK`**。
2. `HUMAN_FINAL_CLICK` 下，Agent **不得自行提交、不得代点平台按钮**（含网页端"生成"按钮）。
3. "全自动 / 目标模式"字样本身**不构成**提交授权，不因此切换到 `AUTONOMOUS_SUBMIT`。
4. 模式写在提交报告里，供离线校验器检查；模式与授权范围矛盾 = 不合规提交。

## 三、LibTV 双通道（独立校验，不得互相顶替）

LibTV 有**两条互相独立的调用路径**，它们的认证状态**不共享**：

| 路由 ID | 路径 | 校验对象 |
|---|---|---|
| `LIBTV_MCP` | LibTV Remote MCP 调用 | MCP 连接与项目上下文 |
| `LIBTV_CLI` | 官方 `libtv` CLI / 本地调用 | 本地 CLI Token |

**核心规则：CLI Token 失效 ≠ MCP 阻断。**

判定顺序（必须按序执行，不得跳步）：

```
1. 先做 LIBTV_MCP 预检
   ├─ 可用 → 走 MCP，记录路由 = LIBTV_MCP，继续
   └─ 不可用 → 记录 MCP 失败原因与错误码，进入第 2 步
2. 再做 LIBTV_CLI 预检（libtv account / libtv project list，只读）
   ├─ 可用 → 走 CLI，记录路由 = LIBTV_CLI，并记一条"MCP 不可用已降级 CLI"
   └─ 不可用 → 记录 CLI 失败原因与错误码，进入第 3 步
3. 两条都不可用 → BLOCKED_LIBTV_AUTH
   落盘错误码与双通道诊断原文 → 进异常队列 → 停止，不得重试、不得改走网页端手工
```

**禁止**：
- 不得在未做另一条路径预检的情况下，仅凭一条路径失败就判定整体阻断。
- 不得以 MCP 可用为理由跳过 CLI 的 Token 检查（反之亦然）：**各查各的**。
- 不得用网页端手工操作替代以上两条路径中的任意一条。

## 四、建节点前置门禁：数量与职责双重校验（本文件最重要的一节）

> **这一节的存在理由**：一次历史生产事故的根因不是平台故障、不是 Token、不是 MCP 不通，
> 而是**门禁放错了位置**。原有校验（`19`）挂在"提交前"，
> 但资产缺失的损害在**创建视频节点的那一刻**就已经发生且不可逆——
> 节点建好、只绑了一张场景图，后面所有生成都会按这个残缺配置走。
> 等到提交前再查，钱已经花在错的东西上了。
>
> **因此：资产校验必须前置到"创建视频节点"之前，且必须同时校验【数量】与【职责】。**

### 4.1 权威清单来自哪（这一条是本节的地基）

**唯一权威源 = `production_contract.json` 的 `assets[]`**，每项形如
`{role, path, purpose}`，`role` 取自固定枚举：

```
character_master / face_identity_master / wardrobe_body_master /
scene_master / prop_master / real_tail_frame / storyboard_composite / keyframe
```

该字段在生产合同 schema 里是**必填且 `minItems: 1`**——所以"要传几项、每项什么职责"
**从来就不是靠 Agent 临场判断，而是合同里已经声明好的。**

### 4.2 校验算法：集合相等，不是"够不够数"

> ⚠️ **"禁止用一张图顶替"这种说法是无效的**——它挡不住"传两张""传四张"。
> 真正可判定的只有一条：**声明集合 == 已绑定集合**（按 `role + sha256` 逐项配对）。

判定 = 以下四类差异**全部为空**才算通过：

| 差异类型 | 含义 | 例子 |
|---|---|---|
| `missing` | 合同声明了，但平台没有绑定项与之配对 | 合同要 9 项，只绑了 1 张场景图 → 8 项 missing |
| `hash_mismatch` | role 对上了，但文件的 sha256 与合同里那份不一致 | 拿错版本的小烬 MASTER |
| `unverified` | 传了、也有节点 ID，但没做第 7 步回读确认 | "调用成功"就当绑定 |
| `undeclared` | 平台绑了合同没声明的东西 | 多绑了张多余的岚 |

**配对键 = `role + sha256`**。用两张、四张都过不去——除非正好等于合同声明的那个集合。
数量是比对的结果，不是比对的标准。

### 4.3 状态分级（承接 Bug 5 的四级模型）

| 级别 | 含义 | 能否建节点 |
|---|---|---|
| `LOCAL_FOUND` | 本地文件存在 | ❌ |
| `LOCAL_QA_PASS` | 本地 QA 通过 | ❌ |
| `PLATFORM_UPLOADED` | 已上传平台 | ❌ |
| `PLATFORM_BOUND_AND_VERIFIED` | 已上传 + 已回读拿到真实节点 ID | ✅（且须通过 4.2 集合比对） |

只有最后一级、且集合相等，才允许建节点。

### 4.4 校验时点（按此顺序，不得跳步）

```
G5 放行（8 项条件全过）
   ↓
【本节】建节点前置门禁 = 数量 + 职责 + 绑定 三项全过
   ↓
才开始 §六 八步流程的第 5 步（创建视频节点）
   ↓
提交（§七 幂等、§九 落盘）
```

**门禁未过 = 不得调用任何建节点接口。** 这不是"建议"，是阻断条件。

### 4.5 门禁必须落盘，可事后审计

每次过门禁必须写一份 `workflow/gates/<gate>_<unit>.token.json`，内容至少包含：

- 校验通过时间、gate 名、unit_id
- **当次实际校验的资产清单快照**（每项：`role` / `path` / `sha256` / 平台节点 ID / 绑定状态）
- **四类差异的对账结果**（`missing` / `hash_mismatch` / `unverified` / `undeclared`，通过时四类皆为空）
- **合同的 sha256**（`contract_sha256`）——合同后续若被改动，令牌自动失效，必须重新校验
- 校验器版本

令牌由 `tools/gate_token.py` 产出，不由 Agent 手写。

**作用**：事后能拿这份快照对照——如果"门禁显示全过"但实际只绑了一张图，
那么对账结果一定对不上，**可以立刻定位是门禁放水还是事后篡改**。
这一条正是为了回答"看板全绿却还是绕了步骤，那到底是谁的问题"。

## 五、认证错误码与停止规则

| 错误码 | 含义 | 必须动作 |
|---|---|---|
| `1100000102` | 非法请求 / Token 无效 | **立即停止当前批量上传**；按 §三 走另一条通道预检；不得继续传后续资产 |
| `NODE_VALIDATION_FAILED` | 节点校验失败（如 `mixed2video` 缺 1~15 个图片/视频参考节点） | 停止建节点；回到 §五第 3 步补齐媒体节点后重试一次；再失败进异常队列 |
| `BLOCKED_LIBTV_AUTH` | 双通道均不可用 | 停止；落盘诊断原文；进异常队列；等用户处理 Token |
| `BLOCKED_CHANNEL_UNAUTHORIZED` | 通道/扣费身份不符（cash、通道不明） | 停止；不得切换 `SHARED→cash` |

**通用停止规则**：
1. 认证类错误一律**先停当前批次**，不做"继续试试"。
2. 停止后做**只读诊断**（`libtv account` / `libtv project list` / MCP 状态）。
3. 落盘：错误码、错误原文、发生步骤、受影响资产/任务、通道。
4. 进异常队列（见 §七），产出 `only_decision` 与 `unblock_condition` 给用户。
5. **不得让用户重讲"LibTV 怎么用"**——诊断信息必须自带。

## 六、LibTV 八步流程（强制顺序，任一步失败即停）

```
1  AUTH_PREFLIGHT（双通道分别校验，见 §三）
2  资产上传（先用 1 张【非生产】测试图验证通道可用，成功才进批量）
3  上传节点回读（拿到平台返回的真实节点 ID，不得假设）
4  资产节点 ID 收集（形成 资产 → 节点ID 映射表）
5  视频节点创建（mixed2video 必须已有真实媒体节点，禁止空手创建）
6  参考图连线（把第 4 步的节点 ID 连到视频节点）
7  视频节点回读（确认连线真实生效，不是"调用成功"就算）
8  生成前校验（preflight：资产、参数、成本、授权）
```

**禁止**：
- **第 2 步失败后继续尝试创建视频节点** —— 这是"节点建了但没资产"的直接成因。
- 用本地文件路径冒充平台媒体节点 ID。
- 把"接口返回成功"当作"资产已绑定"；必须以第 7 步回读为准。

## 七、幂等、超时与重提

- 提交前必须过幂等去重：`idempotency_key = f(unit_id, contract_id, provider, payload)`。
- 命中重复 → **拒绝提交**，并报出已存在的 `task_id` 与其状态，不得再扣一次费。
- **超时先查原任务**：云端任务状态未知时，先续查原 `task_id`，
  **禁止盲目重复提交 / 重复扣费**。
- 每次提交后**立即回填**：真实 `task_id`、实际成本、输出路径、提交时间、平台路由。

## 八、G6 失败后的异常队列

进入异常队列的条目必须包含：
`exception_id` / `unit_id` / `reason` / `evidence` / `only_decision` / `unblock_condition`

本文件新增的 `reason` 取值：

| reason | 触发 |
|---|---|
| `libtv_auth_failed` | 双通道认证均失败（§三第 3 步） |
| `libtv_node_invalid` | 节点校验失败，缺媒体节点（§五第 5 步） |
| `libtv_upload_failed` | 资产上传失败（§五第 2 步） |
| `submission_duplicate` | 幂等键命中重复提交 |
| `timeout_unknown_task` | 超时且原任务状态未知 |

`only_decision` 必须写成**用户可回答的一个决定**（例："更新 LibTV CLI Token 或确认改用 MCP"），
不得写成"请检查系统"。
