# 22｜用户决策交互与版本防循环规则

> 协议版本：3.4 ｜ 生效日期：2026-10-07
> 状态：`ACTIVE_CORE_RULE`
> 目的：让需要用户决定的事项在当前对话中被清楚提出；避免静默改写、空等、重复 QA 或重开 RUN 绕过阻塞。

## 一、先判定改动边界

| 可在已授权范围内执行 | 必须暂停并请用户选择 |
|---|---|
| 拼写、格式、镜头术语规范化；不改变已批准含义的提示词去歧义；补全模型执行所需但不改变创意意图的参数表达 | 改剧情节拍、台词含义、角色行为/能动性、动作类型或接触关系、动作结果/结尾状态、空间转换、用户锁定的机位/镜头边界、生产单元/候选/提交数量、人物/场景/道具身份或外观、模型/平台/时长/分辨率/预算/重试范围，以及任何明确锁定项 |

判定标准：若用户看见前后版本会认为“发生了新的创作选择或授权范围变化”，就是实质变更。QA 的 FAIL/UNCERTAIN 是问题证据，不是改剧情、换资产、扩预算或提交新任务的授权。通用“全自动”“继续”“QA 后提交”只覆盖其明确范围，不等于对任意内容变更的批准。

## 二、用户决定卡（必需）

触及右栏时，先停止依赖该决定的编辑、版本升级、QA、RUN 重建及下游提交。创建一张简短决策卡，至少包含：

1. 决策 ID、项目/段落、RUN、当前版本；当前候选文件路径与 SHA-256（若尚无文件则明确写无）。
2. QA/审查发现及可核验证据；哪些已锁定内容保持不变。
3. 精确描述拟议改动及其影响（镜头、资产、模型、时长、预算、提交次数）。
4. 2–3 个互斥选项，标注推荐项及各自后果；如无需多选项，提供“按现状继续 / 暂停”也可。
5. 一句明确问题、无回复时的默认状态（保持当前稿、不执行依赖步骤）、受影响产物与额度。

决策卡落盘后，必须在**当前面向用户的对话**直接展示这句问题和选项。仅写 `current_owner=user`、`pending_decision`、任务卡或控制台状态，不算完成交接；不得新建窗口/线程来规避等待。用户没有回复时，保持当前版本与 RUN，不能推断同意、不能改版、不能重复审查、不能走依赖该选择的下游。与此决定无关的独立工作可以继续。

## 三、答复与授权记录

- 用户明确选择后，记录原意、选择项、适用文件版本/SHA-256、授权动作及数量/预算边界，再仅执行该范围。
- 对同一文件哈希、同一改动和同一范围，已批准的决定可复用；不得重复询问已回答事项。
- 答复含糊时，只针对缺失的一个关键点追问一次；不得把沉默、过期授权或宽泛目标当成选择。
- 用户明确要求“只分析/只提建议”时，不创建替代稿、不写回权威生产文件。

## 四、QA 与 RUN 防循环

1. 每个候选版本进行一次合并完整审查。发现问题先合并证据和阻断项，禁止多个技能对同一版本串行重复审查。
2. 在不越过第一节边界的轻微修正后，同一问题最多做一次定向复核；仍失败或不确定时，整理决策卡并问用户，不再生成 A/B/C 变体或重复完整 QA。
3. 实质改动获得批准后，另存新版本并只对受影响范围做一次适当 QA；旧文件、旧 QA 和旧 RUN 均保留为历史。
4. 不得为逃避 FAIL、UNCERTAIN、版本锁或用户决定而新建 RUN。协议升级造成旧 RUN 指纹过期时，只在恢复执行时对当前 Gate 重新读取/证明；沿用父 RUN、已用提交次数、已消费预算和审批边界，不得重置额度。
5. 任何 `WAITING_APPROVAL` 必须同时有决策卡路径/ID和当前对话中已发送的问题证据。没有用户可见问题，就不是有效交接，回复必须补问并停在此处。

## 五、短剧示例

- QA 建议把已锁定的“岚侧身躲匕首”改为“隼近身压制并改成平台对峙”：动作关系、距离和结尾状态均变，属于实质改动；先给用户选项，不得直接改成新版本后重审。
- 用户已经批准“匕首擦过岚脸侧并钉在列车外门板”，提示词仅需补充刀尖朝向、门板外侧和命中停留等可见执行细节，且不改变结果时，可在原授权内明确化并按适用规则 QA。

## 六、完成判据

用户待决定事项必须是可直接回答的具体问题。最终状态同时写明：当前版本/哈希、已完成事项、阻塞决定、问题已在当前对话提出与否、未获答复时禁止动作。协议或看板显示“等用户”不能替代实际提问。\n
