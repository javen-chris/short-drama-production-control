# 19｜视频提交前确认报告与内容完整性规则

> 协议版本：3.1 ｜ 最后更新：2026-09-21
> 状态：`ACTIVE_CORE_RULE`（因 2026-09-20 提交事故而制定）
> 事故性质：**用户已授权生成视频（"QA 通过可生视频"），但 Agent 提交时未携带参考资产与完整参数**——"什么都没传就跑视频了"，产出不可用、成本浪费。

**规则目标**：提交前必须有一份**列明全部提交内容**的确认报告，并由校验器确认内容完整、参考资产可用、用户已确认。**"用户有没有授权"和"提交内容对不对"是两件事，两件都要过。**

## 一、提交前确认报告（强制产物）

每次提交前落盘：

```text
<项目>/workflow/submission_reports/<unit_id>_<Vn>.json     ← 机器可校验
<项目>/workflow/submission_reports/<unit_id>_<Vn>.md       ← 人读（推荐）
```

**必填字段**（缺一即不可提交）：

| 类别 | 字段 |
|---|---|
| 标识 | `unit_id`、`run_id`、项目、段 |
| 平台与方式 | `platform`（`runninghub`/`xiaoyunque`/`libtv`/`local`/`other:<名称>`）、`api_mode`（`api`/`workflow_app`/`ui_manual`）、`channel_class`（`member_normal_coins`为默认；`personal_web`需用户指定；`enterprise_shared_cash`需用户明确授权） |
| 模型 | `model`、`model_version`（如 `seedance_2.5`、`rh_h3`） |
| 画面参数 | `duration_seconds`、`resolution`、`fps`、`aspect_ratio` |
| **参考资产** | `reference_assets[]`：每项 `{path, role, qa_status, sha256}` ——**必须逐个列全，不得省略** |
| 提示词 | `prompt` 全文，或 `prompt_sha256` + 存放路径 |
| 成本 | `cost_estimate_cny`、`billing_preflight`：`{api_type, coins_before, coins_after, cash_before, cash_after}` |
| 授权 | `authorization`：`{scope, source, max_submissions, submission_index}` |
| 前置 QA | `qa_gate`：`{g5_review, preflight, assets_all_pass}` |
| 确认 | `confirmed`、`confirmed_at`、`confirmed_via` |

## 二、放行条件（全部满足才允许提交）

按重要性排序——**第 1、2 条就是本次事故的堵漏点**：

1. **参考资产必须齐全可用**：`reference_assets` **非空**（该单元需要参考资产时），且每项：`path` 指向的文件**真实存在**、`qa_status == PASS`、带 `sha256`。**空清单 = 直接阻断**。
2. **提交内容必须完整**：`prompt` 非空（或有可查的 `prompt_sha256`）；`model`、`platform`、`api_mode`、`duration_seconds`、`resolution`、`aspect_ratio` 齐全。
3. `confirmed == true`，且 `confirmed_via` 可追溯到用户消息或确认单。
4. `qa_gate.g5_review == PASS`、`preflight == PASS`、`assets_all_pass == true`。
5. 授权范围覆盖提交：`scope != qa_only`，且 `submission_index <= max_submissions`。
6. 成本在合同预算内，且 `13_模型执行前硬门禁_v3.0.md` 全部通过。
7. 默认 `channel_class` 必须为 `member_normal_coins`，并证明 `api_type == NORMAL`、coins 是唯一扣费余额且 cash 前后不变。`personal_web` 仅在用户指定网页端时允许。`enterprise_shared_cash` 只有 `authorization.source` 中有用户明确cash授权、合同已更新且报告完整时允许；否则 `SHARED`、现金扣费、通道不明或未做前后余额核验 → `BLOCKED_CHANNEL_UNAUTHORIZED`。

任一项不满足 → 状态 `BLOCKED_INCOMPLETE_SUBMISSION`，**禁止提交**；唯一下一步是补齐内容并请用户确认，附报告路径。

## 三、授权范围的判定

| scope | 含义 | 提交次数 |
|---|---|---|
| `qa_only` | 只要求跑到"生成前全部 QA / Prompt 就绪" | **0 次** |
| `test_submission` | 授权一次测试提交（"QA 通过可生视频/跑 720P 测试"） | 1 次 |
| `full_segment` | 授权本段按合同单元完整生成 | 合同单元数 |
| `within_budget` | 授权预算内多次 | 受预算与次数上限约束 |

- 用户说"**QA 检查确认通过，可生视频**" → `scope = test_submission`（或更高）→ **允许提交**，但内容完整性与确认报告一个都不能少。
- "全自动 / 目标模式"字样本身不构成提交授权；指令里出现提交意图才算。
- 超出 scope 的提交（**包括在网页界面手点生成**）算越界。

## 四、自动化目标模式

- **不豁免**：确认报告照样写、照样留档。
- `confirmed` 可引用启动指令，但必须写明 `authorization.source`（指令原文摘要）。
- 指令只授权到 QA → `qa_only` → 停在待提交包，不得自行提交、不得手点平台按钮。
- 提交后**立即回填**：`task_id`、实际成本、输出路径、提交时间。

## 五、平台覆盖（含手动操作）

- 覆盖**所有**视频生成入口：RunningHub API、小云雀（xyq）、LibTV、本地工作流，以及**任何网页界面上手点"生成"的动作**。
- 手点平台同样是提交：先有确认报告，再点按钮。
- 平台界面上的"未提交/草稿"等文案**不能作为状态依据**；以确认报告与台账为准。

## 六、留档与复核

- `workflow/submission_reports/` 即**提交台账**：追加式、不覆盖、不删除。
- 离线校验：`submission_report` 校验器检查报告完整性与上述放行条件；**缺字段、参考资产缺失、条件不满足 = 不合规提交**。
- 台账必须能回答：提交了什么参数、带了哪些参考资产（及其哈希）、谁授权的、花了多少钱、产出在哪。

## 七、禁止

- **禁止零参考资产提交**（该带资产却没带）——本次事故的直接原因。
- 禁止参数不全提交（缺模型/时长/分辨率/比例/平台）。
- 禁止无确认报告提交（任何平台、任何方式）。
- 禁止把"全自动 / 目标模式"理解为提交授权。
- **默认使用消费级 `NORMAL→coins` API。禁止把“RunningHub API/H3”理解为企业级API授权；不得因默认环境变量、API可用性或执行方便自行切换`SHARED→cash`。**
- 用户指定个人网页端时，`api_mode` 必须为 `ui_manual`，不得为了自动化改走 API；未指定网页端时不把网页端擅自当成默认替代。
- 禁止超出 scope、次数、预算提交。
- 禁止提交后不落盘 `task_id` 与实际成本。
- 禁止以平台界面文案推断提交状态。\n
