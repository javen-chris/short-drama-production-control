# 18｜运行轨迹与进度可视规则

> 协议版本：3.5 ｜ 最后更新：2026-10-10
> 状态：`ACTIVE_CORE_RULE`
> 目的：让"Agent 到底做到哪一步、读了什么、卡在哪"**随时可查**，不靠回忆、不靠翻聊天记录。

## 一、存储模型（一段一文件 + 一集一索引）

```text
<项目根>/workflow/
├─ run_index.json          一集/一项目一份：所有段的状态总表
├─ current_unit.json       当前 RUN 的生产单元、版本、Gate、文件哈希与明确授权
└─ runs/
   ├─ RUN-EXAMPLE-U01.json    一段（= 一次运行）= 一个文件，追加式事件日志
   ├─ RUN-EXAMPLE-U02.json
   └─ ...
```

- **一段 = 一次运行 = 一个文件**。一集拆 20 段，就是 20 个段落文件 + 1 个索引，不混、不覆盖。
- 索引记录每段的：`run_id`、**段名**（如 `B-2A（物理格斗）`）、状态、进度（x/y 步）、当前步骤、待决定事项、最后事件时间，以及**当前活跃段 `active_run_id`**。
- 图片与视频产物仍在各自的资产目录；运行轨迹只记"做了什么、读了什么、证据在哪"，**不复制产物**。
- `current_unit.json` 是看板展示当前项目内容的唯一来源；记录 `project_id/run_id/contract_id/unit_id/segment/version/current_gate`、脚本/镜头/资产/Prompt 文件引用与 SHA-256、故事本和视频提交授权。看板不得从旧事件字段猜当前单元。
- 新 RUN 开始前登记当前单元：复制控制台 `examples/current_unit.pending.json`，填写身份与已有文件引用，再运行 `python tools/set_current_unit.py <项目根> <登记文件>`。尚未产出的文件可标为 `pending`；工具只核验和登记，不生成内容或授权动作。
- 创建合同和追加事件都必须核对 RUN、合同、单元、版本及当前引用文件哈希。引用文件更新后先重新登记；否则状态视为过期，不允许 QA 绑定旧内容。
- 资产 `qa_status=PASS` 可在后续步骤复用，但只绑定登记时的 SHA-256：同角色同路径且哈希未变时保留 PASS；文件哈希变化、文件路径/角色变化或首次登记时自动降为 `UNCERTAIN`，须重新独立 QA。其他 Gate 的检查仍按各自范围执行。
- **按变更复核**：同一 RUN 内脚本、镜头或资产的引用与 SHA-256 未变，且检查范围未扩大时，复用对应已通过证据；只补做变化部分与其受影响的下游检查。协议/合同/授权边界变化、QA 规则版本变化、或候选内容实质变化时不得复用相关结论。
- 故事本默认关闭，视频提交默认未授权；登记当前单元不会隐式授予这两项权限。故事本只接受针对本单元的明确授权，授权来源与证据须落盘。

## 二、Agent 的强制义务（用户裁定 2026-09-20）

1. **每完成一步，必须追加一条事件**：`step`、`skill_id`、`protocol_refs`（这一步读了哪些协议文件）、`evidence`（证据文件路径）、`outcome`。使用 schema 已支持的 `at` 和 `elapsed_seconds` 记录完成时刻与耗时；等待原因写入 `pending_decision` 或事件 `reason`。超过 5 分钟仍在处理中可更新索引 `updated_at/current_step` 作为 heartbeat，不得伪造完成事件。普通生产步骤使用 `STEP_COMPLETED` 记录产物事实，不代表 QA 通过；QA 结论只能由独立 QA 角色写入对应 `QA_PASS/QA_FAIL/QA_TIMEOUT`。
   **缺这条记录 = 该步未完成**，不得推进下一步。
2. **每段结束、暂停或切换时更新索引**：状态、进度、待决定事项、`last_event_at`；**新段开始时把 `active_run_id` 指向它**。
3. **跨窗口交接**（Hermes ↔ Codex ↔ 新窗口）：接手方先读索引与当前段文件，再继续；不得凭记忆续接。
4. **禁止伪造**：事件由运行过程产生；手写编造记录等同于伪造证据。G6-S11/S12 的供应商事实应由可信执行器记录真实平台、任务 ID、状态、输出链接和响应证据；填写模型名称不能证明独立 QA 已执行。
5. **Gate 合并与停滞可见**：目标模式下 G1-S02/G2-S03/S04 可将脚本、镜头、生产单元和一次独立复核合并交付；复核结论仍须单独保留 QA 角色证据。同一候选不拆成多个重复 QA 事件。简单任务 10 分钟无事件时，在索引 `pending_decision` 写 `疑似停滞 STALLED`、最后有效事件时间与唯一继续动作；索引 `status` 使用既有枚举，不能写入不受 schema 支持的新状态。RUNNING 必须有近 10 分钟内的实际事件或 heartbeat 支持。
6. **协议升级迁移**：清单指纹变化时，在原 RUN 追加当前阶段的协议迁移记录与新证明；不得要求新建 RUN。迁移保留事件、预算、提交次数、问题、授权和已完成证据，并只使受影响的证明失效。

## 用户待决定状态的必填字段（协议 3.4）

当索引或 RUN 进入 `WAITING_APPROVAL` / `pending_decision`，必须记录 `decision_id`、决策卡路径、候选版本与 SHA-256、需要用户回答的简短原句、影响范围以及问题已在当前对话发送的证据/时间。只有 `current_owner=user` 而缺少这些信息，状态无效；不得把它显示为已完成交接。用户答复后追加原意、选择、授权边界和时间，不覆盖先前事件。未答复前禁止变更候选版本、重建 RUN 或推进依赖 Gate。详见 `22_用户决策交互与版本防循环规则_v3.0.md`。

## 三、用户如何查看

```powershell
# 一集总表：20 段一眼看完，含"当前进行到哪一段"
python -m production_control.run_report <项目目录> --html 运行总表.html

# 实时模式：带「立即刷新」按钮与自动刷新（每 5 秒重新读取磁盘）
python -m production_control.run_report <项目目录> --serve
```

报告页显示：段名、状态、进度、当前步骤、待决定事项、每步读了哪些协议（标注哪些是"必须读"）、证据路径、合规缺口。

**刷新永远是安全的**：数据源就是磁盘上的段落文件与索引，无缓存；新段开始后刷新即出现新行，活跃标记自动跟随。

## 四、段清单：段号与段名的权威数据（用户维护）

```text
<项目根>/workflow/segments.json     ← 用户录入：有哪些段、每段叫什么
```

```json
{
  "project": "EXAMPLE-SERIES-EP01",
  "series": "示例系列",
  "episode": "EP01",
  "segments": [
    {"segment": "U01", "title": "B-2A（物理格斗）", "note": "开门即打"},
    {"segment": "U02", "title": "B-3D（人物躲避爆炸）", "note": ""}
  ]
}
```

- **用户是这份文件的作者**：可在实时页面（`--serve`）直接录入、改名、加删段，也可手写。页面上的「保存段清单」按钮即视为用户确认写入。
- **Agent 必须读它取段名**：启动某一段时，若调用方未指定 `segment_title`，**必须从本文件读取该段的名称**作为 `segment_title`；不得自行另起名字。
- **Agent 新建段时必须回写**：如果流程产生了段清单里没有的段，要把它补进本文件，保持两边一致。
- 名字冲突时：**段名以本文件为准，运行状态以段落轨迹文件为准**（改名不会重置进度）。
- 校验：段号不可为空、不可重复；文件必须是合法 JSON。不符的录入会被拒绝并回显原因。
- 页面与 Agent 共用同一份文件 → **你在页面上看到的段名，就是 Agent 用的段名**。

## 五、与"读取证明"的分工

| 规则 | 证明什么 | 时机 |
|---|---|---|
| `15_协议读取与合规证明_v3.0.md` | 开工前**读过当前版本协议**（指纹 + 哈希 + 挑战问答） | 任务启动、协议更新后 |
| 本规则 | 运行中**每一步做了什么**（事件日志 + 索引） | 每步完成时 |

两者都由 `run_compliance` 复核：**完成却没有记录 = 不合规**。

## 六、禁止

- 禁止把运行轨迹放到项目外的临时目录（换窗口就找不到）。
- 禁止只写索引不写段落文件，或反之——索引是摘要，段落文件才是原始记录。
- 禁止为"清理"删除既有段落文件；历史是证据，只能归档。
- 禁止在段落文件里省略 `protocol_refs` 与 `evidence`（那会让这一步无法复核）。\n
