# 协议读取与合规证明

> 协议版本：3.5 ｜ 最后更新：2026-10-10

> 状态：`ACTIVE_CORE_RULE`
> 目的：解决一个无法靠自觉解决的问题——**Agent 声称"已读取协议"，怎么证明？**

## 一、问题定义

自动化生产线上的 Agent（Hermes / Codex / 其他窗口）可能在以下情况下出错：

- 声称读取了核心协议，实际凭聊天记忆或旧版本开工；
- 读的是过期版本，规则已经更新而不自知；
- 引用了不存在的"协议条款"来自圆其说。

本规则给出**可机器校验**的读取证明，不依赖 Agent 的自我声明。

## 二、机制：指纹 + 读取证明 + 挑战问答

三个独立检查，全部通过才算合规：

1. **协议指纹（manifest fingerprint）**
   指纹工具实际位于控制台仓库 `短剧生产线控制台/tools/protocol_fingerprint.py`，不是本协议目录。维护者从控制台目录运行：
   ```powershell
   py -3 tools/protocol_fingerprint.py generate --root "<PROTOCOL_ROOT>"
   py -3 tools/protocol_fingerprint.py check --root "<PROTOCOL_ROOT>"
   ```
   工具扫描唯一注册表引用的协议文件及通用底线文件，生成 `protocol_manifest.json`：每份文件的 SHA-256、整体指纹与挑战问题（答案只存哈希）。清单是完整校验目录，不表示每个任务都必须读完清单中的所有文件。

2. **按 RUN/Gate 读取证明（read proof）**
   Agent 先建立 RUN 执行合同（仅建卡，不开始生产），再按当前合同 Gate 读取协议并提交 PROTOCOL_ATTESTATION（`protocol_attestation.schema.json`）。范围固定为通用底线文件 + `skill-chain.json` 中本 RUN 当前 Gate 的适用协议引用；同 Gate 的连续步骤合并为一个读取包，不要求预读后续 Gate。证明必须带 RUN、任务、合同、Gate 和覆盖步骤 ID，不能由 Agent 自选更小范围。校验器比对：声明哈希 = manifest 哈希 = 磁盘实际哈希，并与合同绑定。

3. **相关挑战问答（challenges）**
   每个 RUN 首次证明回答一条通用协议版本题，以及一条从当前 Gate 已读协议相关题目中选出的挑战（若该 Gate 没有专属题，则只答通用题）。同一 RUN 后续 Gate 只回答该 Gate 的相关挑战；通用协议文件和版本题可在同一 manifest 指纹下复用。同 Gate 的多个步骤合并一次证明。**答案在 manifest 里只存哈希**，无需回答无关 Gate 的题目。

## 三、执行要求

- **何时必须提交**：每个新 RUN 开始生产前，以及进入尚未证明的新 Gate 前；同 Gate 连续步骤沿用同一证明。相同 RUN、相同 manifest 指纹下，已验证的通用文件哈希与通用挑战答案复用，不得重复生成 G0/G1 通用证明。协议指纹变化后，旧证明失效；只重新证明当前 Gate 涉及的变更范围和挑战。
- **校验方式**：
  ```powershell
  python tools/protocol_attestation.py --plan --project-root <项目目录> --run-id <RUN-ID>
  # 阅读计划列出的文件后，填写 attestation JSON，再提交校验：
  python tools/protocol_attestation.py <attestation.json> --project-root <项目目录> --run-id <RUN-ID>
  ```
  `--plan` 输出 `PLAN_NOT_PROOF`，只代表清单预览；提交校验后输出 `PASS` / `REJECTED`（附具体失败项）。PASS 证明按 RUN 合同和 Gate 写入轨迹。
- **REJECTED 的后果**：当前 Gate 不得写入生产事件或推进；补齐当前 Gate 缺少的协议读取后，重新提交该 Gate 的 attestation。不得"先干活后补证明"。
- **协议变更后**：任何人修改核心协议文件，必须从控制台仓库重生成并检查 manifest。已有 RUN 不得因指纹变化而重建；先使用 `py -3 tools/migrate_run_protocol.py <项目目录> --run <RUN-ID> --inspect` 输出保存版本之间的文本差异及当前/后续/无关范围。影响本合同的变更须提供逐项 `--confirmed-path` 与 `--confirmation-evidence`，才在原 RUN 更新对应哈希并追加迁移记录；仅无关变更可直接登记。身份、授权、QA 路由仍属必查基础规则。当前证明涉及变更时标记 STALE 并重验对应范围；未改变的范围可沿用。旧事件、预算、提交消费次数、Task ID、授权与 attestation 历史保留，缺失旧文本明确标 UNKNOWN。
- **编排器集成**：`orchestrator` 的每个审批断点在放行前检查当次任务的 attestation 状态；`run_state` 事件中保留 attestation_id 作为证据。

## 四、诚实声明：这套机制防什么、不防什么

- **防得住**：没读文件就开工、读了旧版本、编造条款、复制粘贴旧 attestation（指纹对不上）。
- **防不住**：Agent 真读了文件但"读了没照做"。这一层由已经代码化的硬约束兜底（schema / 校验器 / 编排器断点）——协议里最重要的规则都已落成机器检查，不遵守就过不了关。
- 两条防线的关系：attestation 证明"输入是对的"，校验器证明"输出是对的"。

## 五、attestation 块格式

```json
{
  "attestation_id": "ATT-20260920-001",
  "task_id": "TASK-EXAMPLE-01",
  "agent": "codex",
  "manifest_fingerprint": "<64位指纹>",
  "read_files": [{"path": "00_自动化生产唯一入口_v3.0.md", "sha256": "<64位>"}],
  "answers": [{"id": "image-model", "answer": "gpt-image-2"}],
  "declared_at": "2026-09-20T17:00:00+08:00"
}
```

`read_files` 必须覆盖通用底线文件与本 RUN 当前 Gate 协议包；`answers` 必须回答通用挑战和当前 Gate 相关挑战。验证 PASS 后，校验器会将证明写入该 RUN；轨迹写入端拒绝没有当前 Gate 有效证明的正式事件。进入新 Gate 时再次读取并证明新 Gate 范围。\n
